01

¿Por qué un orquestador?

El pipeline ya funciona; falta quién lo corra

Orquestación

cron corre comandos; un orquestador corre pipelines

cron es perfecto para un comando suelto. En cuanto hay dependencias, reintentos y reprocesos, cada equipo termina reinventando un orquestador malo con scripts.
Orquestación

Qué hace y qué no hace Airflow

Sí hace

  • Decide cuándo corre cada tarea y en qué orden.
  • Reintenta, registra estados y guarda los logs.
  • Recupera días perdidos (catchup) y reprocesa rangos (backfill).
  • Una UI para ver, pausar y relanzar.

No hace

  • No procesa datos: los procesa tu código, Polars, dbt, Spark o el warehouse.
  • No es una herramienta de streaming (Capítulo 4).
  • No mueve datos entre tareas: por XCom solo viajan cosas chicas.

Alternativas: Luigi (sesión 1.1), Dagster, Prefect; en la nube, Cloud Composer y Amazon MWAA (Airflow gestionado), Workflows o Step Functions.

02

Arquitectura de Airflow 3

Componentes, base de metadatos e instalación

Arquitectura

Los componentes

El dag-processor lee los archivos y los guarda serializados; el scheduler crea corridas y manda tareas al executor; los workers corren tu código y reportan al API server. En Airflow 3 las tareas no tienen acceso directo a la base.
Arquitectura

Lo nuevo en Airflow 3

Cambio en Airflow 3Qué significa para ti
API server en lugar del webserverLa UI nueva y la API REST v2 salen del mismo proceso
Task SDK: from airflow.sdk import dag, taskEl import estable para escribir DAGs
Las tareas hablan con la Execution APITu tarea ya no puede (ni debe) consultar la base de Airflow
catchup=False por omisiónSi quieres recuperar el pasado, lo pides explícito
Un cron es un disparological_date = momento del disparo; el intervalo de un día es opcional
Backfill dentro del schedulerairflow backfill create, también desde la UI
Datasets ahora se llaman assetsProgramar por datos en lugar de por horario (sesión 3.2)

Si buscas en internet, fíjate en la versión: casi todo lo que encuentres es de Airflow 2.

TaskFlow

Tu primer DAG con TaskFlow


from airflow.sdk import dag, task

@dag(schedule=None, start_date=..., catchup=False)
def hola_taskflow():
    @task
    def extraer():
        return [{"id": 1, "total": 250.0}, ...]

    @task
    def transformar(pedidos: list[dict]):
        validos = [p for p in pedidos if p["total"] > 0]
        return {"validos": len(validos)}

    @task
    def cargar(resumen: dict):
        print(f"Cargaría {resumen['validos']} pedidos")

    cargar(transformar(extraer()))

hola_taskflow()
  • Llamar a las funciones no las ejecuta: arma el grafo.
  • Pasar el resultado de una a otra crea la dependencia.
  • Lo que se regresa viaja como XCom: guardado en la base de Airflow.

airflow dags test hola_taskflow corre una vez en tu terminal, sin scheduler: así se prueba mientras escribes.

04

El tiempo en Airflow

Cada corrida tiene su fecha

Fecha lógica

¿Qué fecha «es» cada corrida?

Lo medimos en el lab con reloj.py. En Airflow 3, schedule='0 6 * * *' crea la corrida del 08 a las 06:00 del 08. Con CronDataIntervalTimetable se comporta como Airflow 2: la del 08 se crea el 09, al cerrar el intervalo.
Fecha lógica

Los parámetros del horario

ParámetroQué controlaEn tienda_diaria
scheduleCuándo se dispara: cron, @daily, un timedelta, un asset o None"0 6 * * *"
start_dateLa primera fecha lógica posible. Fija, nunca now()08/09 06:00, CDMX
end_dateLa última (opcional)22/09 06:00
catchup¿Crear las corridas que se perdieron desde start_date?True
max_active_runsCuántas corridas del DAG a la vez1: en orden
zona horariaLa de start_date; por omisión, UTCAmerica/Mexico_City
Idempotencia

Idempotente por fecha

Mal

@task
def transformar():
    hoy = date.today()
    correr(hasta=hoy, salida="lakehouse")

Un backfill del 08/09 corre con la fecha de hoy y pisa lo publicado.

Bien

@task
def transformar(ds=None):
    correr(hasta=ds,
           salida=f"lakehouse/corte={ds}")

El resultado depende solo de ds y de bronze. Correrlo hoy o en un año da lo mismo.

Es la idempotencia de la 1.2, ahora con fecha: misma entrada y misma fecha, mismo resultado, y en su partición.

Backfill

catchup y backfill

catchup

Al despausar, el scheduler crea las corridas que faltan desde start_date. Con catchup=False, solo de ahora en adelante.

backfill

Tú pides un rango, aunque esas corridas ya existan:


airflow backfill create --dag-id tienda_diaria \
  --from-date 2026-09-08T06:00:00-06:00 \
  --to-date   2026-09-12T06:00:00-06:00 \
  --reprocess-behavior completed \
  --dry-run          # primero, en seco

none

Solo crea las fechas que no tienen corrida.

failed

Además repite las que fallaron.

completed

Repite todo el rango, aunque haya salido bien.

Las fechas del backfill son instantes. Las corridas son a las 06:00 de CDMX; si pones --to-date 2026-09-12, eso es la medianoche y el 12 queda fuera.
Backfill

La trampa: el backfill corre en paralelo

Lo vimos en el lab: el backfill no respeta el max_active_runs del DAG; tiene su propio --max-active-runs. El diseño por partición y el puntero que nunca retrocede hacen que no importe.
Operación

Volver a correr lo que falló


# llegó la carga del 22: reintenta solo lo que falló
airflow tasks clear tienda_diaria \
  -s 2026-09-22 -e 2026-09-23 --only-failed -y
  • clear borra el estado; el scheduler vuelve a correr esas tareas.
  • El 22 sin carga: las revisiones fallan y transformar queda upstream_failed. Nadie escribió un if.
  • Con la carga rota: transformar sale con código 2 y vigente.txt se queda en el 21. Falla cerrada.

Proyecto final

Su práctica como DAG


@dag(schedule="*/10 * * * *", start_date=..., catchup=False,
     max_active_runs=1)
def vuelos_raw_bronze():
    @task.bash(cwd=PROYECTO)
    def extraer(script: str):
        return f"python extractores/{script}"

    extracciones = [
        extraer.override(task_id=f"extraer_{a}")(s)
        for a, s in [("cq", "extraer_cq_api.py"),
                     ("jg", "extraer_jg_sftp.py"),
                     ("xj", "extraer_xj_mysql.py")]]

    @task.bash(cwd=PROYECTO, trigger_rule="all_done")
    def cargar_bronze():
        return "python bronze/cargar_bronze.py"

    extracciones >> cargar_bronze()
  • Es su correr_todo.py, pero con estado por paso y en paralelo.
  • trigger_rule="all_done": si JG falla, CQ y XJ igual se cargan.
  • catchup=False: aquí la fecha no importa; cada extractor sabe hasta dónde llegó por su checkpoint.

Lo terminan en la entrega E4, con reintentos y alertas de la 3.2.

Contraste importante con tienda_diaria: aquí no hay fecha lógica que procesar, porque las fuentes son incrementales con checkpoint. Por eso catchup=False.
Resumen

Para llevar

  1. Un orquestador envuelve tus comandos: orden, reintentos, historia y reprocesos.
  2. Airflow 3: dag-processor, scheduler, workers y API server; standalone para aprender.
  3. TaskFlow: @task y pasar resultados arma el grafo; por XCom viaja poco.
  4. Cada corrida procesa su fecha (ds), nunca «hoy».
  5. catchup y backfill son seguros si cada día escribe su partición.
