Anatomía de la ingesta

Antes de escribir código: de dónde, cómo y a dónde

Patrones

Push o pull

En la práctica conviven: el proveedor te empuja un CSV y tú jalas la API de pedidos.

Push y pull cambian quién tiene la responsabilidad de avisar. En push necesitas vigilar que el archivo llegue (frescura); en pull, no saturar a la fuente.
Diseño

Seis preguntas antes de ingestar

¿De quién es la fuente?

Dueño, contacto y a quién avisar cuando cambie.

¿Cada cuánto cambia?

Define la frecuencia y si conviene incremental.

¿Completa o incremental?

¿Traigo todo o solo lo nuevo? (sesión 1.3)

¿Cuánto volumen?

Filas por día, tamaño de archivo, límites de la API.

¿Hay contrato?

Esquema, formato y reglas acordadas por escrito.

¿Datos sensibles?

Datos personales o financieros: cifrado y acceso mínimo.

La mayoría de los incidentes de ingesta no son técnicos: el proveedor cambió el formato y nadie avisó. Por eso importa el contrato.
Diseño

La landing zone

Principios: raw es inmutable y se guarda tal cual (permite reprocesar); bronze ya tiene tipos y metadatos; lo que no pasa el contrato va a cuarentena, nunca a la basura.

02

Archivos

El CSV parece simple hasta que llega el de otro proveedor

Archivos

Ocho trampas del CSV

Codificación

UTF-8, Windows-1252, Latin-1… o UTF-8 con BOM.

Delimitador

Coma, punto y coma, pipe o tabulador.

Decimales y miles

1.234,50 frente a 1,234.50

Fechas

¿03/04/2026 es marzo o abril?

Comillas

«Cuaderno, 100 hojas» contiene el delimitador.

Filas malformadas

Un campo de más, un «N/D» donde va un número.

Ceros a la izquierda

El SKU «00123» no es el número 123.

Encabezados

«Descripción», «DESCRIPCION», «nombre»…

Los tres archivos del laboratorio traen casi todas estas trampas a propósito. Pedir que adivinen cuál trae cuál antes del lab.

Archivos

Detectar para descubrir, contratar para operar

Detección automática

  • charset-normalizer sugiere la codificación.
  • csv.Sniffer sugiere el delimitador.
  • Útil el primer día con un proveedor nuevo.
  • Peligrosa como mecanismo diario: un día adivina distinto.

Si el archivo cambia, queremos que el pipeline falle, no que se adapte en silencio.

Archivos

¿Qué hacemos con las filas malas?

Fallar todo

Seguro, pero una fila mala detiene miles de buenas.

Descartar en silencio

El peor: los totales no cuadran y nadie sabe por qué.

Cuarentena + umbral

Lo bueno sigue, lo malo queda guardado con motivo, y si hay demasiado, se detiene.

El umbral (5 % en el kit) es una decisión de negocio, no técnica. Debe acordarse con el dueño de los datos.

Se puede agregar al final y leer por partes: ideal para logs, páginas de API y streaming. pd.read_json(..., lines=True).

Archivos

De CSV a Parquet

CSVParquet
Tipos de datoTodo es texto; hay que interpretarGuardados en el archivo
EsquemaImplícito en el encabezadoEmbebido y verificable

En el laboratorio lo medirás: con 40 filas gana CSV; con cientos de miles, Parquet gana por mucho.

Por eso raw guarda el CSV tal cual (fidelidad) y bronze lo guarda en Parquet (eficiencia).

Idempotencia con archivos


def aterrizar_archivo(ruta, fuente, contrato, landing, fecha):

    copiar_a_raw(ruta)                      # tal cual llegó
    df, rechazadas = leer_con_contrato(ruta, contrato)
    ...
    escribir_atomico(destino_bronze, df.to_parquet)
    Manifiesto(landing).registrar(hash=h, estado="ok", ...)
  • El hash del contenido, no el nombre: el proveedor puede mandar dos veces «inventario.csv» con datos distintos.
  • Escritura atómica: temporal y luego renombrar.
  • El manifiesto se escribe al final: si algo falla antes, la próxima corrida lo reintenta.

APIs

El problema del offset

Si la fuente cambia mientras paginas, el offset se recorre: duplicas unos registros y pierdes otros.

Mitigaciones: paginar por cursor o keyset, ordenar por una llave estable, y siempre validar el total y los duplicados al final (como hace el kit).
APIs

Límites de tasa

Cómo lo avisa la API

  • 429 Too Many Requests
  • Retry-After: 1: «vuelve en 1 segundo».
  • Algunas mandan X-RateLimit-Remaining para frenar antes de chocar.

Cómo respondes

  • Respetar Retry-After si viene.
  • Si no, backoff exponencial.
  • Nunca reintentar en un ciclo sin espera.
El token bucket es el algoritmo más común. La API caprichosa del lab usa uno de 4 fichas por segundo.
APIs

Backoff exponencial con jitter

Exponencial: la espera máxima se duplica en cada intento, hasta un tope.

Jitter: se elige al azar entre 0 y ese máximo, para que mil clientes no reintenten en el mismo instante.

Referencia: Marc Brooker, 'Exponential Backoff and Jitter', AWS Architecture Blog. Sin jitter, los reintentos sincronizados de muchos clientes vuelven a tumbar al servidor.
APIs

¿Qué se reintenta y qué no?

Situación¿Reintentar?Por qué
Timeout o error de conexiónSí, con backoffSuele ser pasajero
429 Too Many RequestsSí, respetando Retry-AfterVas demasiado rápido
500, 502, 503, 504Sí, con backoffFalla temporal del servidor
400 Bad RequestNoTu solicitud está mal: repetirla da lo mismo
401 / 403NoCredencial inválida o sin permiso
404 Not FoundNo (casi nunca)El recurso no existe

Y solo si la operación es idempotente: un GET se puede repetir; un POST que cobra una tarjeta, no (a menos que uses una Idempotency-Key).

Reintentar un 401 seis veces solo retrasa el error y puede bloquear la cuenta. Fallar rápido también es robustez.

El cliente robusto, en 20 líneas


def get_con_reintentos(sesion, url, *, params=None, headers=None, max_intentos=6, timeout=(3.05, 10)):
    for intento in range(1, max_intentos + 1):
        try:
            r = sesion.get(url, params=params, headers=headers, timeout=timeout)
        except (requests.Timeout, requests.ConnectionError) as e:
            motivo, espera = type(e).__name__, espera_backoff(intento)
        else:
            if r.status_code < 400:
                return r                                        # éxito
            if r.status_code not in REINTENTABLES:              # 400, 401, 403, 404...
                raise ErrorNoReintentable(f"HTTP {r.status_code} en {url}")
            motivo = f"HTTP {r.status_code}"
            espera = _retry_after(r) or espera_backoff(intento)  # respeta Retry-After
        if intento < max_intentos:
            evento("http_reintento", url=url, motivo=motivo, intento=intento, espera_s=espera)
            time.sleep(espera)
    raise ReintentosAgotados(f"{url}: {max_intentos} intentos (último: {motivo})")

En producción puedes usar urllib3.Retry o tenacity. Escribirlo una vez te enseña qué configurar en ellos.

Versión simplificada del kit (cliente_http.py). En el lab verán ambas: urllib3.Retry para las APIs bien portadas y esta para la caprichosa.
APIs

Descargas largas: checkpoints

  • Después de cada página guardada, se guarda el cursor siguiente.
  • Si la ingesta cae en la página 7, la próxima corrida continúa en la 7.
  • Al terminar, se consolida, se valida contra el total y se borra el checkpoint.

// landing/_checkpoints/pedidos_2026-09-29.json
{"cursor": "eyJvIjogMTUwfQ==", "pagina": 3}

Orden importa: primero la página, luego el checkpoint. Al revés, podrías saltarte una página.

Manejo de errores

Principios

  • Nunca except: pass.
  • Excepciones con nombre: ErrorCalidad, ReintentosAgotados…
  • El mensaje dice qué, dónde y con qué dato.
  • Una fuente que falla no debe tumbar a las demás, pero el resultado final sí debe reportar la falla.
Código de salidaSignificado
0Todo bien
1Al menos una fuente falló
2Error de configuración

El orquestador (Airflow en el Capítulo 3) solo ve el código de salida. Un script que termina en 0 cuando falló es un script que miente.

Resumen

Para llevar

  1. La ingesta empieza con preguntas: dueño, frecuencia, volumen, contrato y sensibilidad.
  2. raw inmutable, bronze con tipos y metadatos, cuarentena para lo que no cumple.
  3. Un contrato explícito por fuente vale más que cualquier detección automática.
  4. Paginación estable, timeouts siempre y reintentos solo para errores temporales.
  5. Secretos fuera del código, logs como datos y códigos de salida honestos.
